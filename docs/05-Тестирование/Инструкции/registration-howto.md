# Как подготовить материалы для регистрации программы для ЭВМ (HOWTO)

> Пошаговая инструкция по использованию скриптов из `scripts/registration_4_7/`.
> Актуально для задачи 4.7 и для повторного формирования материалов в будущих
> задачах (например, через пару месяцев, когда функционал объектов разойдётся).

---

## 1. Что это и зачем

Скрипты формируют из **одной кодовой базы** пакет документов для регистрации
одного или нескольких регистрационных объектов:

1. **PDF-распечатка исходного кода** (до 70 страниц, фрагменты);
2. **Реферат** (аннотация ≤ 700 знаков, тип ЭВМ, язык, ОС, объём);
3. **Данные для официальной формы заявки** (заполняет куратор/патентовед).

Главная идея — **«один манифест на регистрационный объект»**. Вся логика
генерации общая, а состав каждого объекта описывается отдельным `manifest.yaml`.

---

## 2. Требования и установка

Требуется Python 3.10+ и системный шрифт `DejaVuSansMono` (TTF, входит в
большинство дистрибутивов Linux; используется для кода, т.к. содержит кириллицу).

```bash
cd scripts/registration_4_7
python3 -m venv --system-site-packages .venv
./.venv/bin/pip install -r requirements.txt
```

Зависимости: `reportlab` (генерация PDF), `PyYAML` (чтение манифестов),
`pypdf` (проверка PDF).

> Флаг `--system-site-packages` позволяет использовать уже установленные в
> системе пакеты; `requirements.txt` докачает недостающие.

---

## 3. Состав скриптов

| Файл | Назначение | Когда запускать |
| --- | --- | --- |
| `common.py` | чтение манифеста, сбор файлов, приоритеты отбора | — (библиотека) |
| `generate_printout.py` | генерация PDF-распечатки | каждый раз при изменении кода |
| `measure_source_size.py` | замер объёма исходников | при заполнении реферата |
| `verify_printout.py` | проверка PDF на соответствие формату | после генерации |
| `verify_abstract.py` | проверка реферата | после правки реферата |

Все команды выполняются из каталога `scripts/registration_4_7/` через
`./.venv/bin/python`, пути — относительно корня репозитория (`../../...`).

---

## 4. Структура каталога для нового объекта

Для каждого регистрационного объекта заводится свой каталог с манифестом и
артефактами. Рекомендуемая раскладка:

```text
docs/registration_<код_задачи>/
├── README.md                    # описание задачи, статус, открытые вопросы
├── object_<id>/
│   ├── manifest.yaml            # главный входной файл (описываем вручную)
│   ├── abstract.md              # реферат (описываем вручную)
│   ├── data_for_application.md  # данные для формы заявки (вручную)
│   └── printout/
│       ├── printout.pdf         # генерируется скриптом
│       └── report.json          # отчёт о составе распечатки (генерируется)
```

Пример для задачи 4.7: `docs/registration_4_7/object_a/` и `object_b/`.

## 5. Манифест: описание полей

Файл `manifest.yaml` — единственный источник правды о составе объекта.

```yaml
object:
  id: A                          # короткий идентификатор (для отчётов)
  working_title: "..."           # рабочее название (используется, пока нет официального)
  official_title: null           # официальное название (заполняет куратор)
  description: >                 # краткое описание (для титульного листа и реферата)
    ...
  focus:                         # список ключевых функций (для реферата)
    - "..."

application_data:                # данные для официальной формы (заполняет куратор)
  owner: null
  authors: []
  creation_date: null
  contacts: null

source:                          # откуда брать исходный код
  include_extensions: [".php", ".js", ".vue"]   # какие расширения включать
  exclude_patterns: ["*.spec.js", "*.test.js", "*.md"]  # что исключать
  backend:                       # пути к бэкенду (каталоги и файлы)
    - {path: "api/src/Ibs/Context/...", type: directory}
    - {path: "api/src/.../file.php", type: file}
  frontend:                      # пути к фронтенду
    - {path: "frontend/src/...", type: directory}

printout:                        # параметры генерации PDF
  target_max_pages: 65           # бюджет страниц кода (с титульным листом ≤ 70)
  format:
    page_size: "A4"
    orientation: "portrait"
    margins: {top: "20 мм", right: "20 мм", bottom: "20 мм", left: "25 мм"}
    font_size: "12 pt"
    page_numbering:
      start_from: 2              # нумерация начинается с 2 (стр. 1 — титульный лист)
    line_wrap: true
  selection:                     # стратегия отбора фрагментов (см. раздел 6)
    strategy: all                # all | fragments
    priority: [ "**/Service/**", "**/Entity/**", ... ]
```

### Важно про `exclude_patterns`

Паттерны применяются и к имени файла, и к относительному пути. Обязательно
исключайте тесты (`*.spec.js`, `*.test.js`) и документацию (`*.md`), иначе они
попадут в распечатку.

---

## 6. Стратегии отбора фрагментов

Общий лимит распечатки — **70 страниц** (включая титульный лист). Поэтому
`target_max_pages` кода ставим с запасом (обычно 65).

- **`strategy: all`** — включить все файлы из `source`. Подходит, когда объект
  небольшой и целиком укладывается в лимит (пример: объект A — 52 стр.).

- **`strategy: fragments`** — отобрать файлы по списку `priority`
  (glob-паттерны, от наиболее значимых к наименее), пока не исчерпан бюджет
  `target_max_pages`. Остальные файлы попадают в `excluded_files` отчёта.
  Подходит, когда полный объём кода превышает лимит (пример: объект B — полный
  код 161 стр., отобрано 67).

### Как задавать `priority`

Список glob-паттернов в порядке убывания значимости. Файлы, совпавшие с
паттерном раньше, попадают в распечатку первыми. Обычно приоритет такой:

```yaml
priority:
  - "**/Service/**"          # бизнес-логика
  - "**/State/**"            # провайдеры/процессоры API
  - "**/Repository/**"
  - "**/Filter/**"
  - "**/Entity/Treatment.php"  # ключевые сущности поимённо
  - "**/Entity/**"             # остальные сущности
  - "**/stores/*.js"           # фронтенд: сторы
  - "**/components/**/*.script.js"
  - "**/utils/*.js"
  - "**/api/*.js"
```

> Для наиболее важных сущностей можно перечислить их поимённо выше общего
> паттерна `**/Entity/**` — так гарантированно попадёт именно ядро домена.

## 7. Пошаговый сценарий для нового объекта

### Шаг 1. Завести каталог и манифест

```bash
mkdir -p docs/registration_<код>/object_<id>/printout
```

Создать `manifest.yaml` по образцу из раздела 5. Заполнить `source` реальными
путями и выбрать `selection.strategy`.

### Шаг 2. Сгенерировать PDF и посмотреть на объём

```bash
cd scripts/registration_4_7
./.venv/bin/python generate_printout.py \
  --manifest ../../docs/registration_<код>/object_<id>/manifest.yaml \
  --out ../../docs/registration_<код>/object_<id>/printout/printout.pdf \
  --report ../../docs/registration_<код>/object_<id>/printout/report.json
```

Скрипт печатает JSON-отчёт: сколько файлов включено/исключено и число страниц.

### Шаг 3. Проверить PDF

```bash
./.venv/bin/python verify_printout.py \
  --pdf ../../docs/registration_<код>/object_<id>/printout/printout.pdf \
  --manifest ../../docs/registration_<код>/object_<id>/manifest.yaml
```

Ожидаемый вывод — `[OK] распечатка соответствует требованиям задачи 4.7`.

Если число страниц превышает 70 или в отчёте много исключённых «важных»
файлов — откорректировать `priority`/`target_max_pages` и перегенерировать.

### Шаг 4. Замерить объём исходников

```bash
./.venv/bin/python measure_source_size.py \
  --manifest ../../docs/registration_<код>/object_<id>/manifest.yaml
```

Вывод вида: `Объём исходников: 73018 байт (71.3 КБ)`. Это значение подставить
в реферат (раздел «Объём программы в машиночитаемой форме»).

### Шаг 5. Написать реферат (`abstract.md`)

Структура (обязательные разделы):

```markdown
## Название программы
## Аннотация            # ≤ 700 знаков с пробелами
## Тип реализующей ЭВМ
## Язык программирования
## Вид и версия операционной системы
## Объём программы в машиночитаемой форме
```

Аннотация должна покрывать: **назначение**, **область применения**,
**функциональные возможности**.

### Шаг 6. Проверить реферат

```bash
./.venv/bin/python verify_abstract.py \
  --abstract ../../docs/registration_<код>/object_<id>/abstract.md
```

### Шаг 7. Заполнить `data_for_application.md`

Структурированные сведения для куратора: название (рабочее и официальное),
правообладатель, авторы, дата создания, краткое описание, контакты. Поля,
которые неизвестны, помечать «ожидается от куратора».

### Шаг 8. Обновить README задачи

Зафиксировать статус выполнения и список открытых вопросов куратору.

## 8. Правило распределения общего кода (два объекта из одной базы)

Когда из одной кодовой базы регистрируется несколько объектов, действует
правило: **каждый файл принадлежит ровно одному объекту**.

- Общие служебные модули относим к тому объекту, чью основную функциональность
  они обеспечивают (например, `SecurityIdentity`, базовый API-клиент — к
  клинической части).
- Файлы-«витрины» конкретных функций (фармакогенетика, витальные показатели) —
  к соответствующему CDSS-объекту.
- Это же правило задаёт границы `source` в манифестах: пути объектов не должны
  пересекаться.

## 9. Типичные проблемы и как их решать

| Проблема | Причина | Решение |
| --- | --- | --- |
| `[error] шрифт не найден` | нет DejaVuSansMono | установить пакет `fonts-dejavu-core` |
| `No module named 'reportlab'` | не активировано venv | запускать через `./.venv/bin/python` |
| PDF > 70 страниц | стратегия `all`, а код большой | переключить на `fragments` + `priority` |
| в отчёт попали тесты | не исключены `*.spec.js` | добавить в `exclude_patterns` |
| `verify` не видит номер страницы | нумерация сбилась | проверить `page_numbering.start_from` |
| важный файл не попал в распечатку | низкий приоритет | поднять его паттерн в `priority` |
