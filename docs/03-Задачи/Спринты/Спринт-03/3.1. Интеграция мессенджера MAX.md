# 3.1. Интеграция мессенджера MAX

## Основание
Пункт 3 письма куратора (`01-Куратор/Письма/Оптимальные возможности программы к 20 сентября.md`): пациент вносит дозу через чат-бот по персональному коду; MAX — основной канал уведомлений (Telegram в резерве). Задача интегрирует канал MAX в схему уведомлений (FUNC-021).

## Навыки (Skills)
`git-workflow`, `explain-db`, `run-tests`, `write-adr`, `write-instruction`

## Бизнес-логика

Задача реализует двустороннюю интеграцию MAX (FUNC-021): исходящие уведомления и фундамент входящего канала (привязка `chat_id` пациента).

- **Сущность каналов** — `PatientChannelIdentity`: отдельный контакт пациента на каждый канал (`sms`/`email`/`push`/`max`), значение — телефон/email/push-токен/chat_id; уникальность `(patient_id, channel_type)`, CRUD-API с фильтром по `patientId`.
- **Отправка через MAX** — `MaxChannel` (POST `{MAX_API_URL}/messages`, `Authorization: {MAX_BOT_TOKEN}`): адрес из `PatientContactResolver`, текст ≤ 4000 символов без HTML, троттлинг 0.5 с; временные ошибки (`5xx`/сеть) ретраятся с экспоненциальной задержкой (1с→5с→25с), `4xx` — без повторов; при отсутствии адреса/недоступности канала — лог `failed`.
- **Привязка `chat_id` (персональный код)** — врач получает защищённый диплинк `GET /api/patients/{id}/max-deeplink` (случайный токен, таблица `max_deeplinks`); пациент открывает бота → событие `bot_started` → токен резолвится в `patientId` и сохраняется контакт `max` (`chat_id`).
- **Входящий канал** — Long Polling (`app:communication:collect-max-contacts`, контейнер `max-updates-listener`) и Webhook `POST /api/max/webhook` (проверка `X-Max-Bot-Api-Secret`, активация на деплое).
- **Приём дозы через бота** — задача 4.3; в 3.1 заложена инфраструктура привязки контакта и входящего канала.
- **Связь с ЭИБ и уведомлениями** — каждая отправка логируется в `notification_log` (привязка к пациенту/лечению, статус, `externalId`); данные пациента отмечаются отдельно.

Полное описание: [[Каналы связи (PatientChannelIdentity) и интеграция мессенджера MAX]].

## Сценарии

> Черновик аналитика: позитивные и негативные. Security-сценарии дополняет Эйприл.

### Контакты каналов

#### СЦ-3.1.1. Создание контакта MAX для пациента (позитивный)
Дано врач в карточке пациента
И у пациента ещё нет контакта для канала "max"
Когда врач сохраняет контакт канала "max" со значением chat_id "42342534"
Тогда создаётся PatientChannelIdentity с channelType="max" и value="42342534"
И контакт связывается с patientId пациента

#### СЦ-3.1.2. Дубликат контакта на канал (негативный)
Дано у пациента уже есть контакт для канала "max"
Когда врач пытается сохранить второй контакт для канала "max"
Тогда система отклоняет сохранение
И возвращает ошибку уникальности (patient_id + channel_type)

#### СЦ-3.1.3. Некорректное значение контакта (негативный)
Дано врач сохраняет контакт канала "max"
Когда значение value пустое, длиннее 255 символов или содержит пробелы
Тогда система отклоняет сохранение
И возвращает ошибку валидации

### Привязка chat_id через диплинк (персональный код)

#### СЦ-3.1.4. Выдача диплинка врачу (позитивный)
Дано врач авторизован
И у пациента есть карточка
Когда врач запрашивает GET /api/patients/{id}/max-deeplink
Тогда система возвращает ссылку https://max.ru/<бот>?start=<token>
И токен сохраняется в max_deeplinks с привязкой к patientId

#### СЦ-3.1.5. Привязка chat_id при bot_started (позитивный)
Дано пациенту выдан диплинк с токеном
Когда пациент открывает бота по диплинку
И MAX присылает событие bot_started с payload=<token> и chat_id
Тогда система резолвит токен в patientId
И создаёт/обновляет PatientChannelIdentity (channelType="max", value=chat_id)

#### СЦ-3.1.6. Неизвестный токен в bot_started (негативный)
Дано MAX присылает событие bot_started
Когда payload содержит токен, которого нет в max_deeplinks
Тогда система молча игнорирует событие
И контакт не создаётся

### Отправка уведомлений

#### СЦ-3.1.7. Отправка уведомления через MAX (позитивный)
Дано у пациента настроен контакт канала "max" (chat_id)
И канал MAX доступен
Когда врач отправляет уведомление пациенту через канал "max"
Тогда система резолвит chat_id через PatientContactResolver
И MaxChannel отправляет сообщение на этот chat_id
И в notification_log фиксируется status="sent" с recipientAddress=chat_id

#### СЦ-3.1.8. Контакт канала не настроен (негативный)
Дано у пациента нет контакта для канала "max"
Когда врач отправляет уведомление через канал "max"
Тогда система не вызывает канал
И в notification_log фиксируется status="failed" с ошибкой "Address not configured"

#### СЦ-3.1.9. Канал недоступен (негативный)
Дано контакт "max" настроен
Но канал MAX недоступен (isAvailable=false)
Когда система пытается отправить уведомление через "max"
Тогда канал не вызывается
И в notification_log фиксируется status="failed" "Channel is not available"

#### СЦ-3.1.10. Временная ошибка MAX → экспоненциальные ретраи (позитивный/негативный)
Дано контакт "max" настроен
Когда MAX отвечает 5xx при отправке
Тогда система повторяет отправку с экспоненциальной задержкой (1с → 5с → 25с)
И при успехе фиксирует status="sent"
Иначе фиксирует status="failed" после исчерпания повторов

#### СЦ-3.1.11. Слишком длинный текст (негативный)
Дано контакт "max" настроен
Когда текст уведомления превышает 4000 символов
Тогда система отклоняет отправку до HTTP-запроса
И фиксирует ошибку

### Входящий канал (Webhook)

#### СЦ-3.1.12. Webhook с неверным секретом (негативный; security — на доработку Эйприл)
Дано MAX отправляет событие на POST /api/max/webhook
Когда заголовок X-Max-Bot-Api-Secret отсутствует или неверен
Тогда система возвращает 403
И событие не обрабатывается

### Приём дозы через бота (входящий поток → задача 4.3, перспектива)

#### СЦ-3.1.13. Пациент вносит дозу (перспектива 4.3)
Дано пациент привязан к боту (контакт max сохранён)
Когда пациент отправляет дозу в чат с ботом
Тогда система сохраняет дозу с источником "внесено пациентом"
И данные отражаются в ЭИБ с отметкой источника

#### СЦ-3.1.14. Некорректная доза (перспектива 4.3)
Дано пациент привязан к боту
Когда пациент отправляет дозу в некорректном формате (не число или вне диапазона)
Тогда система отклоняет ввод
И просит повторить дозу

## Реализация

### План разработки

##### 2. Сущность `PatientChannelIdentity`

**Модуль:** `Ibs\Context\Communication\Entity`

**Таблица:** `patient_channel_identities`

**Поля:**

- `id` — первичный ключ (IDENTITY).
    
- `patientId` — `int`, NOT NULL (внешняя ссылка на пациента, но без FK в БД, чтобы не создавать жёсткую зависимость между контекстами).
    
- `channelType` — `string(32)`, NOT NULL (`sms`, `email`, `push`, `max`).
    
- `value` — `string(255)`, NOT NULL (телефон/email/push-токен/chat_id).
    
- `createdAt`, `updatedAt` — `datetime` (по желанию, но удобно).
    

**Индексы:**

- Уникальный `(patient_id, channel_type)` — один контакт на канал для пациента.
    

**Валидация:**

- `Assert\NotBlank` на `patientId`, `channelType`, `value`.
    
- `Assert\Length(max=255)` на `value`.
    
- `Assert\Regex('/^[^\s]+$/')` на `value` (без пробелов), особенно для `max` и `push`.
    

**Методы:** геттеры/сеттеры, конструктор без обязательных параметров (пустая сущность) или с обязательными, но при API-создании лучше пустой.

##### 4. API для контактов каналов

- `#[ApiResource]` на `PatientChannelIdentity`.

- API может быть использован фронтендом для отображения и редактирования контактов (особенно MAX chat_id) в карточке пациента.
    

##### 5. Сервис `PatientContactResolver`

**Модуль:** Communication\Service

- Метод `get(int $patientId, string $channelType): ?string`.
    
- Ищет `PatientChannelIdentity` по `patientId` и `channelType`, возвращает `value` или `null`.
    
- Используется `NotificationService` для получения адреса перед отправкой.
    

**Почему это важно:**  
`NotificationService` больше не обращается к `Recipient->phone/email/maxUserId`, а спрашивает резолвер. Это позволяет добавлять новые каналы без изменения `Patient` и `Recipient`.

##### 6. Обновление `ChannelInterface`

##### 6.1. Новая сигнатура `send()`

php

public function send(
    Recipient $recipient,
    string $address,
    NotificationMessage $message
): SendResult;

- `$recipient` — только для `patientId`/`treatmentId` (не содержит адресов).
    
- `$address` — конкретный адрес, полученный из `PatientContactResolver`.
    
- `$message` — как раньше.
    

##### 6.2. Обновить `Recipient`

Убрать поля `phone`, `email`, `pushToken`, `maxUserId` и метод `addressFor`. Оставить:

php

public function __construct(
    public readonly ?int $patientId = null,
    public readonly ?int $treatmentId = null,
) {}

Это сильно упрощает модель и убирает дублирование контактов.

##### 6.3. Обновить `FakeChannel`

- В тестах проверять, что `address` передан корректно.
    

##### 6.4. Обновить `MaxChannel`

- Принимает `$address` как `chat_id`.
    
- Больше **не** обращается к `$recipient->maxUserId`.
    
- Остальная логика (HTTP-запрос, проверка длины, разбор ответа) без изменений.
    

##### 7. Обновление `NotificationService`

##### 7.1. Резолв адреса перед отправкой

В `deliver()` для каждого канала:

1. `$address = $this->contactResolver->get($recipient->patientId, $channelType);`
    
2. Если `$address === null`:
    
    - Логировать `failed` с ошибкой `Address not configured for channel ...`.
        
    - Для `IMMEDIATE` пробрасывать `NotificationDeliveryException`.
        
    - Для `ROUTINE` продолжать со следующим каналом.
        
3. Если адрес есть — передавать его в `sendWithRetries()`.
    

##### 7.2. Ретраи

- Логика `sendWithRetries` остаётся, но теперь `attemptSend()` вызывает `$channel->send($recipient, $address, $resolvedMessage)`.
    

##### 7.3. Логирование

- В `NotificationLog` сохраняем `recipientAddress = $address`.
    
- Поле `externalId` — из `SendResult`.
    

##### 8. Конфигурация `MaxChannel`

- Параметры `MAX_API_URL`, `MAX_BOT_TOKEN`, `MAX_ENV`.
    
- В `services.yaml` зарегистрировать `MaxChannel` с явными аргументами.
    
- Убрать автопривязку строковых аргументов (иначе `autowire` упадёт).
    

##### 9. Тестирование

##### 9.1. Unit `PatientContactResolver`

- Возвращает адрес по patientId и channelType.
    
- `null`, если записи нет.
    
- Кэширование (опционально) — не обязано.
    

##### 9.2. Unit `MaxChannel` (новая сигнатура)

- Успешная отправка: проверка URL, заголовков, тела и `chat_id` из `$address`.
    
- `5xx` → `retryable=true`.
    
- `4xx` → `retryable=false`.
    
- Текст > 4000 → `InvalidArgumentException` до HTTP-запроса.
    
- Пустой `address` → `failure`.
    
- `isAvailable()`.
    

##### 9.3. Unit `NotificationService`

- Резолвер возвращает адрес → канал вызван с этим адресом.
    
- Резолвер возвращает `null` → `failed`, канал **не вызывается**.
    
- Ретраи временных ошибок (первичная + до трёх повторов).
    
- Критические ошибки без повторов.
    
- Асинхронный ROUTINE через Messenger.
    
- Обработчик конверта.
    

##### 9.4. Integration `PatientChannelIdentity`

- Сохранение и получение контакта через EntityManager.
    
- API тест: создание/обновление контакта через API Platform.
    

##### 9.5. Обновить существующие тесты

- Все тесты, где создаётся `Recipient`, `FakeChannel`, `NotificationService`, должны быть адаптированы к новой сигнатуре и отсутствию адресов в `Recipient`.
    

##### 10. Финальные проверки

- `doctrine:schema:validate` — «in sync».
    
- Все backend-тесты зелёные.
    
- Frontend-тесты зелёные (фронтенд не затрагивается, но проверка не помешает).
    
- Убедиться, что `MAX_BOT_TOKEN` не попал в Git.
