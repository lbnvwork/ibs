### Описание

**Задача 2.25. Добавление поля «Вес» в витальные показатели (только backend, без удаления)**

- **Спринт:** 2  
- **Код:** 2.25  
- **Оценка:** 0.5 дня  
- **Функция:** FUNC-017 (Дашборд врача)  
- **Статус:** К выполнению  

**Цель:**  
Добавить в модель витальных показателей поле `weight` (вес пациента в кг) с возможностью создания и редактирования через существующий API. Кэш последних значений `patient_vitals_latest` должен автоматически поддерживаться в актуальном состоянии при добавлении или изменении записей. Удаление показателей не предусмотрено.

**Исходное состояние:**  
- Задача 2.21 выполнена: таблицы `patient_vitals` и `patient_vitals_latest` созданы, API (POST, PUT) и сервис `PatientVitalsSyncService` работают для Hb, ЧСС, систолического/диастолического АД, сатурации.  
- Поле `weight` отсутствует.

**Требования:**

1. **Миграция БД**  
   - Добавить поле `weight DOUBLE PRECISION NULLABLE` в таблицу `patient_vitals`.  
   - Добавить поле `weight DOUBLE PRECISION NULLABLE` в таблицу `patient_vitals_latest`.  
   - Обновить CHECK-ограничение `chk_at_least_one` для `patient_vitals`, включив в него `weight` (запись только с одним весом допустима).

2. **Сущности Doctrine**  
   - В `PatientVitals` добавить свойство `weight` (`?float`), геттер/сеттер, группы сериализации `patient_vitals:read`, `patient_vitals:write`.  
   - В `PatientVitalsLatest` добавить свойство `weight` (`?float`), геттер/сеттер (только для сервиса).

3. **Валидация**  
   - Для `weight` в `PatientVitals`:  
     - `Assert\Positive` (строго больше 0).  
     - `Assert\LessThanOrEqual(300)` (верхняя граница).  
   - Кастомное ограничение `AtLeastOneVitalSign` расширить: теперь оно учитывает и `weight`.  
   - Удаление через API не предусмотрено: эндпоинт `DELETE /api/patient_vitals/{id}` должен быть отключён или защищён (например, через настройку API Platform `collectionOperations` и `itemOperations` без `delete`). Принято решение: удаление не реализуем.

4. **Сервис `PatientVitalsSyncService`**  
   - Метод `syncLatest(int $patientId)` вызывается только при создании (POST) и обновлении (PUT).  
   - Добавить в него обработку `weight`:  
     - `SELECT weight FROM patient_vitals WHERE patient_id = :pid AND weight IS NOT NULL ORDER BY record_dt DESC LIMIT 1`  
     - Полученное значение (или NULL) записать в `patient_vitals_latest.weight`.  
   - Так как удаления нет, пересчёт кэша при удалении не требуется.

5. **Тестирование (ручное)**  
   - **Создание:** `POST /api/patient_vitals` с `weight: 70.5`. Проверить, что запись создалась, в `patient_vitals_latest` появился `weight = 70.5`.  
   - **Создание без веса:** `POST` без поля `weight`. Кэш сохраняет предыдущее значение 70.5.  
   - **Редактирование:** `PUT` существующей записи с `weight: 68.0`. Кэш обновляется на 68.0.  
   - **Редактирование с удалением веса:** `PUT` той же записи, явно передаём `weight: null`. В кэше `weight` становится `null`, если других записей с весом нет.  
   - **Валидация:** `weight: -5` → 422, `weight: 350` → 422, `weight: 0` → 422.  
   - **Пустой вес:** передача только `weight` (остальные показатели null) допустима, если нет других не-null полей – запись создаётся, кэш обновляется.

**Ожидаемый результат:**  
- Поле «Вес» доступно при создании и редактировании витальных показателей.  
- Кэш `patient_vitals_latest.weight` корректно синхронизируется при любых изменениях.  
- Удаление показателей заблокировано, кэш не требует пересчёта при удалении.

**Файлы для доработки:**  
- Миграция, сущности `PatientVitals`, `PatientVitalsLatest`, валидатор `AtLeastOneVitalSign`, сервис `PatientVitalsSyncService`, настройка API Platform (запрет DELETE для `PatientVitals`).

**Зависимости:**  
- Строго после 2.21.  
- После завершения этой задачи можно приступать к фронтенду (2.22, 2.23) с гарантией, что `weight` уже присутствует в API.
