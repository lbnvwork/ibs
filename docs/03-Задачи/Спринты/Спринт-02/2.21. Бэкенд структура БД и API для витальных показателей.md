**Цель:**  
Создать таблицы для хранения истории витальных показателей пациентов (`patient_vitals`) и кэша последних значений (`patient_vitals_latest`). Реализовать API для внесения и получения данных, а также сервисный слой, автоматически обновляющий кэш при добавлении или изменении записей.

**Исходное состояние:**  
- Витальные показатели (Hb, ЧСС, АД, сатурация) в БД не хранятся.  
- `test_history` содержит только МНО и не предназначена для раздельного ввода давления или пульса.  
- Дашборд врача показывает только МНО и комментарий.

**Требования:**

1. **Миграции БД**
   - Создать таблицу `patient_vitals`:

     | Поле | Тип | Ограничения |
     |------|-----|-------------|
     | id | SERIAL | PRIMARY KEY |
     | patient_id | INTEGER | NOT NULL, FK → patients(id) ON DELETE CASCADE |
     | treatment_id | INTEGER | NULLABLE, FK → treatments(id) ON DELETE SET NULL |
     | record_dt | TIMESTAMP(0) | NOT NULL, DEFAULT NOW() |
     | hb | DOUBLE PRECISION | NULLABLE |
     | heart_rate | INTEGER | NULLABLE |
     | systolic_pressure | INTEGER | NULLABLE |
     | diastolic_pressure | INTEGER | NULLABLE |
     | saturation | INTEGER | NULLABLE |
     | comment | TEXT | NULLABLE |
     | created_at | TIMESTAMP(0) | NOT NULL, DEFAULT NOW() |
     | updated_at | TIMESTAMP(0) | NOT NULL, DEFAULT NOW() |

   - Добавить CHECK-ограничение `chk_at_least_one`: хотя бы одно из полей `hb`, `heart_rate`, `systolic_pressure`, `diastolic_pressure`, `saturation` должно быть не NULL.
   - Создать индексы:
     - `idx_vitals_patient_record` (patient_id, record_dt DESC) — для быстрого поиска последних значений.
     - `idx_vitals_treatment` (treatment_id) — для связи с лечением.

   - Создать таблицу `patient_vitals_latest`:

     | Поле | Тип | Ограничения |
     |------|-----|-------------|
     | patient_id | INTEGER | PRIMARY KEY, FK → patients(id) ON DELETE CASCADE |
     | hb | DOUBLE PRECISION | NULLABLE |
     | heart_rate | INTEGER | NULLABLE |
     | systolic_pressure | INTEGER | NULLABLE |
     | diastolic_pressure | INTEGER | NULLABLE |
     | saturation | INTEGER | NULLABLE |
     | last_updated | TIMESTAMP(0) | NOT NULL, DEFAULT NOW() |

   - Никаких CHECK на `patient_vitals_latest` не нужно: строка может быть полностью из NULL (если пациент есть, но ни одного показателя ещё не введено — тогда запись создаётся при первом вводе).

2. **Сущности и API**
   - Создать сущность `PatientVitals` (для таблицы `patient_vitals`), зарегистрировать её в API Platform с группами сериализации.
     - POST /api/patient_vitals — создание новой записи.
     - PUT /api/patient_vitals/{id} — редактирование (только значение, дату, комментарий; нельзя менять patient_id).
     - DELETE /api/patient_vitals/{id} — удаление (при удалении должен перестраиваться кэш `patient_vitals_latest` для этого пациента).
   - Создать сущность `PatientVitalsLatest` (только для чтения). API для дашборда будет забирать эти поля через JOIN с patients, отдельный эндпоинт для `patient_vitals_latest` не требуется (но сущность нужна для Doctrine и сервиса).
   - Валидация на уровне сущности `PatientVitals`:
     - `record_dt` — NotBlank, Type(DateTimeInterface).
     - Числовые поля (если указаны) — Positive, диапазоны: Hb 50–250, ЧСС 30–250, АД (оба) 70–250, сатурация 50–100.
     - Кастомное ограничение `AtLeastOneVitalSign`: проверяет, что хотя бы одно из полей hb, heart_rate, systolic_pressure, diastolic_pressure, saturation не равно null.

3. **Сервис `PatientVitalsSyncService`**
   - Метод `syncLatest(int $patientId): void` — вызывается после создания, обновления или удаления `PatientVitals`.
   - Логика:
     - Проверить существование записи в `patient_vitals_latest` по `patient_id`. Если нет — создать новую.
     - Для каждого из пяти показателей:
       - Выполнить `SELECT <field> FROM patient_vitals WHERE patient_id = :pid AND <field> IS NOT NULL ORDER BY record_dt DESC LIMIT 1`.
       - Если значение найдено — записать его в соответствующее поле `patient_vitals_latest`.
       - Если значение не найдено (все записи для этого показателя удалены или их не было) — установить поле в NULL.
     - Обновить `last_updated = NOW()`.
   - Сервис должен быть оформлен как Symfony Service (автоинжектинг EntityManagerInterface, PatientVitalsLatestRepository).
   - Интеграция с API Platform:
     - Через Event Listener на `postWrite` (или State Processor Decorator) для `PatientVitals` вызывать `syncLatest` после успешной записи.
     - При удалении (`preRemove` или `postRemove`) также вызывать `syncLatest`.

4. **Обработка удаления пациента**
   - Благодаря FOREIGN KEY с `ON DELETE CASCADE`, при удалении пациента автоматически удаляются все его записи из `patient_vitals` и из `patient_vitals_latest`. Никаких дополнительных действий в сервисе не требуется.

**Ожидаемый результат:**
- Миграции создают обе таблицы с корректными связями и индексами.
- API позволяет создавать, редактировать и удалять записи витальных показателей с валидацией.
- При любом изменении `patient_vitals` кэш `patient_vitals_latest` автоматически синхронизируется.
- Данные готовы для использования в дашборде (задача 2.23) и для будущих задач аналитики.

##### Этап 5. Интеграция сервиса с событиями Doctrine

Чтобы автоматически вызывать `syncLatest` при изменениях в `patient_vitals`, зарегистрировать Event Subscriber (или Listener) на события `postPersist`, `postUpdate`, `preRemove` (или `postRemove`). В listener'е получать patient_id из объекта `PatientVitals` и вызывать `syncLatest($patientId)`.

Альтернативно можно декорировать State Processor для `PatientVitals` и вызывать синхронизацию после вызова родительского процессора. Это более современный подход для API Platform 3. Но проще и быстрее использовать Doctrine Listener.

Рекомендую создать `PatientVitalsListener` с методами `postPersist`, `postUpdate`, `postRemove` (или `preRemove`). В случае `preRemove` нужно запомнить patient_id перед удалением, либо использовать `postRemove`, где объект уже не managed, но можно получить id через `LifecycleEventArgs->getObject()` перед удалением. Лучше использовать `preRemove`: сохранить patient_id в listener и в `postRemove` (или прямо в `preRemove` вызвать синхронизацию с задержкой через `OnFlush`, но проще сделать так: в `preRemove` получить patientId и сохранить в свойство, а в `postRemove` выполнить синхронизацию). Однако есть особенность: `preRemove` не позволяет делать flush, но вызов сервиса (который делает flush) внутри `postRemove` разрешён. Поэтому сделаем два метода:

```php
public function preRemove(LifecycleEventArgs $args): void {
    $entity = $args->getObject();
    if ($entity instanceof PatientVitals) {
        $this->patientId = $entity->getPatient()->getId();
    }
}
public function postRemove(LifecycleEventArgs $args): void {
    if ($this->patientId) {
        $this->syncService->syncLatest($this->patientId);
        $this->patientId = null;
    }
}
```

Для `postPersist` и `postUpdate` просто вызываем `syncLatest($entity->getPatient()->getId())`.

Зарегистрировать подписчик в `services.yaml` или с помощью атрибута `#[AsDoctrineListener]`.

**Ожидаемый результат:** при любом изменении `patient_vitals` кэш обновляется автоматически.
