# 2.30. Заполнение колонки «Рекомендации» текстом SMS

## Основание
В таблице истории болезни для строк-назначений показывать текст SMS, отправленного по этому назначению. Хвост спринта 2; готовит тексты уведомлений к спринту 4 (письмо куратора, п.5).

## Финальная постановка
<!-- Эйп (Лид): единый промт для разработчика. Ниже — исходная постановка (сохранена). -->

**Цель:**
В таблице истории болезни для каждой строки, соответствующей **назначению** (appointment), отображать текст SMS, которое было отправлено пациенту именно по этому назначению. Для записей анализов и витальных показателей колонка «Рекомендации» остаётся пустой.

**Исходное состояние:**
- Таблица `appointments` содержит поле `sms_id` (FK → `sms_out.id`).
- В `sms_out` хранится текст сообщения (`text`), дата создания и привязка к лечению.
- При загрузке истории болезни API не возвращает текст связанного SMS для назначений.
- Индекс по полю `sms_id` в таблице `appointments` отсутствует.

**Требования:**
1. **Индекс для оптимизации** — создать индекс `idx_appointments_sms_id` на поле `sms_id` таблицы `appointments`. Ускорит JOIN при выборке назначений с их SMS.
2. **Бэкенд: расширение данных о назначениях** — при формировании списка событий истории болезни для каждого назначения с ненулевым `sms_id` загружать связанное SMS из `sms_out` (используя индекс) и добавлять поле `smsText` в ответ API. Если `sms_id = NULL` или SMS не найдено, `smsText = null`. Для анализов (`test_history`) и витальных показателей (`patient_vitals`) SMS не загружаются.
3. **Фронтенд: отображение в таблице** — в колонке «Рекомендации» для строк назначений выводить `smsText`, если он не `null`; иначе ячейка пустая. Для анализов и витальных показателей колонка всегда пустая.
4. **Динамическое обновление** — данные загружаются при открытии карточки и переключении пациентов, колонка обновляется автоматически.

**Ожидаемый результат:**
- Врач видит текст SMS, отправленного по каждому назначению, в строке назначения в колонке «Рекомендации».
- Назначения без SMS и другие события (анализы, витальные) не содержат текста.
- Производительность JOIN обеспечена индексом.

**Примечание:** индекс `idx_appointments_sms_id` добавить через миграцию перед реализацией бэкенда. Текущий внешний ключ `fk_6a41727abd5c7e60` гарантирует целостность, но не создаёт индекс автоматически (в PostgreSQL для FK индекс не создаётся неявно).
