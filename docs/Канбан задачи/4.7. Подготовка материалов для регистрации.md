### Ход разработки

Отличный момент, и его надо решить до генерации документов, иначе получится два почти одинаковых PDF.

## 1. Как сделать «красиво»: одна кодовая база → два регистрационных объекта

Вместо того чтобы вручную готовить два набора файлов, закладываем модель **«один манифест на регистрационный объект»**.

Суть:

- Общий генератор один.
- Для каждой регистрации заводится свой `manifest.yaml`.
- В манифесте описано:
  - официальное название объекта;
  - назначение/функции;
  - перечень путей к каталогам/файлам исходников;
  - правила исключения (`tests`, `*.spec.js`, стили и т.п.);
  - целевой объём в страницах.
- Генератор по манифесту собирает отдельный PDF-документ.
- Отдельно считается объём исходных файлов именно для этого объекта.

Тогда:

- два разных PDF;
- два разных реферата;
- два набора данных для куратора;
- общая инфраструктура генерации и проверки;
- при изменении кода достаточно пересобрать оба манифеста.

### Правило владения общим кодом

Чтобы два пакета не содержали одинаковых фрагментов, вводим правило:

> Каждый файл исходного кода принадлежит только одному регистрационному объекту.

Общие служебные модули относим к тому объекту, чью основную функциональность они обеспечивают.

Например:
- `SecurityIdentity` → в объект B, так как это общая система доступа клинической части;
- `shared/api/client.js` → в объект B;
- `pharmacogenetics.js`, `vitals.js` → в объект A, так как это витрина CDSS-функций.

## 3. Что генерируем для каждой из двух регистраций

### Для каждого объекта готовим

1. **PDF-распечатка исходного кода**
   - свой титульный лист-заглушка;
   - свои фрагменты кода;
   - свой целевой объём ≤ 65 страниц кода, чтобы с титульным листом суммарно не превысить 70;
   - форматирование по требованиям: A4, поля 20/20/20/25, шрифт 12 pt, нумерация начинается с 2.

2. **Реферат**
   - аннотация ≤ 700 знаков с пробелами;
   - свои назначение, область применения, функциональные возможности;
   - свой расчётный объём исходников.

3. **Данные для куратора**
   - блок с названием, правообладателем, авторами, датой создания, контактами, кратким описанием;
   - саму официальную форму заявки не заполняем, отдаём структурированный `data_for_application_a.md` и `data_for_application_b.md`.

## 5. План работ с учётом двух объектов

1. **Зафиксировать официальные названия двух объектов**  
   Пока используем рабочие названия A и B.

2. **Создать манифесты**  
   `object_a/manifest.yaml` и `object_b/manifest.yaml`.

3. **Написать генератор**  
   Один Python/ReportLab скрипт, который вызывается так:
   ```bash
   python scripts/registration_4_7/generate_printout.py \
     --manifest docs/registration_4_7/object_a/manifest.yaml \
     --out docs/registration_4_7/object_a/printout/printout.pdf
   ```

4. **Подготовить два реферата**  
   С отдельным расчётом объёма по каждому манифесту.

5. **Подготовить два набора данных для куратора**  
   Без заполнения официальной формы.

6. **Прогнать тест-кейсы**  
   Для каждого PDF и реферата отдельно:
   - A: `TC-A-4.7-1 ... TC-A-4.7-4`
   - B: `TC-B-4.7-1 ... TC-B-4.7-4`

7. **Закоммитить**  
   Техническую генерацию и артефакты; форму заявки не добавляем, так как это зона куратора.

## 6. Что нужно подтвердить с твоей стороны

1. Какие именно два объекта регистрируются?  
   Нужны официальные или рабочие названия.

2. Подходит ли предложенный сплит:  
   - A = CDSS/фармакогенетика/витальные данные;  
   - B = клиническая система ведения пациентов и терапии.

3. Курируются ли оба патента одними авторами/правообладателем?  
   Если да, куратор получит два одинаковых блока данных, отличающихся только названием и описанием.

4. Общий код можно не дублировать в обоих PDF?  
   Я предлагаю правило «один файл — только в одном объекте».
