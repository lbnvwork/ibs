# Каналы связи (PatientChannelIdentity) и интеграция мессенджера MAX

> Бизнес-логика. Функция: **FUNC-021 «Коммуникации — каналы связи и напоминания»**.
> Источник: письмо куратора `01-Куратор/Письма/Оптимальные возможности программы к 20 сентября.md` (пп. 1, 3, 5, 8).
> Задачи: `3.1. Интеграция мессенджера MAX`, `3.2. Унификация каналов связи и проектирование схемы уведомлений`; приём дозы из бота — `4.3`.

---

## 1. Контекст и назначение

К 20 сентября программа должна вести законченный цикл консультации пациента. Коммуникация идёт через каналы связи:

- **MAX** — основной мессенджер для уведомлений, **Telegram — в резерве**, **SMS** — альтернатива/резерв (пп. 1, 5 письма).
- Для каждого пациента **тип уведомления настраивается персонально** (п. 1).
- Пациент может **самостоятельно вносить дозу препарата**, в том числе через **чат-бот в мессенджере** по **персональному коду** (п. 3).
- Отправка рекомендаций и их **доставка отслеживаются**, в истории болезни формируется отметка (п. 8).

Задача **3.1** реализует двустороннюю интеграцию MAX:

- **исходящую** — отправка уведомлений пациенту через канал `max`;
- **входящую (фундамент)** — приём событий MAX (Long Polling / Webhook) и **привязка `chat_id` пациента** через защищённый диплинк.

«Персональный код» из письма куратора в 3.1 реализован как **случайный токен в защищённом диплинке** (раздел 4): он идентифицирует пациента при первом обращении к боту и привязывает его `chat_id`. Сам **приём дозы** через бота — задача **4.3**; здесь под него заложена инфраструктура входящего канала и привязки контакта.

## 2. Каналы связи и сущность `PatientChannelIdentity`

### 2.1. Зачем отдельная сущность

Раньше контакты пациента (телефон, email, push-токен, MAX-идентификатор) хранились полями в `Recipient`/`patients`. Это создавало жёсткую связь: каждый новый канал требовал правок модели пациента и получателя.

Сущность `PatientChannelIdentity` выносит контакты в отдельную таблицу — **один контакт на один канал на пациента**. Новый канал добавляется без изменения `Patient` и `Recipient` (в `Recipient` остаются только `patientId`/`treatmentId`).

### 2.2. Каналы и значение адреса

| `channelType` | Смысл `value` (адрес доставки) |
| --- | --- |
| `sms` | номер телефона |
| `email` | адрес электронной почты |
| `push` | push-токен устройства |
| `max` | `chat_id` диалога/чата пациента в MAX |

### 2.3. Поля

- `patientId` — ссылка на пациента (целочисленная, без внешнего ключа между контекстами).
- `channelType` — тип канала (`sms`, `email`, `push`, `max`).
- `value` — адрес/идентификатор в канале (телефон / email / push-токен / chat_id).
- `createdAt`, `updatedAt` — служебные отметки времени.

### 2.4. Ограничения, валидация и API

- **Уникальность** `(patient_id, channel_type)` — для пациента не может быть двух контактов одного канала.
- `patientId`, `channelType`, `value` — обязательные (NotBlank).
- `channelType` ≤ 32 символа, `value` ≤ 255 символов и **без пробелов** (актуально для `max` и `push`).
- Сущность доступна как API-ресурс (CRUD) с фильтром `SearchFilter` по `patientId` — врач видит/правит контакты конкретного пациента (в т.ч. `chat_id`).

**Бизнес-смысл:** у пациента может быть несколько каналов, но в каждом канале — ровно один актуальный адрес.

## 3. Схема исходящих уведомлений

Единая точка отправки — `NotificationService`. Он скрывает от вызывающего кода детали каналов, применяет приоритет и логирует каждую попытку.

### 3.1. Приоритеты доставки

| Приоритет | Назначение | Способ доставки |
| --- | --- | --- |
| `IMMEDIATE` | критические алерты | синхронно, ошибка пробрасывается вызывающему коду |
| `ROUTINE` | напоминания и рассылки | через очередь (Messenger), fallback на синхронную отправку |

### 3.2. Резолв адреса перед отправкой

Для каждого канала `NotificationService` спрашивает адрес у `PatientContactResolver::get(patientId, channelType)`:

1. **Адрес найден** → адрес передаётся в канал: `channel->send(recipient, address, message)`.
2. **Адрес не найден** (`null`):
   - логируется `failed` с ошибкой `Address not configured for channel ...`;
   - для `IMMEDIATE` — пробрасывается исключение доставки;
   - для `ROUTINE` — переход к следующему каналу.
3. **Канал не зарегистрирован / недоступен** → логируется `failed`, отправка не выполняется.

### 3.3. Отправка через `MaxChannel`

- Запрос `POST {MAX_API_URL}/messages` (базовый URL `https://platform-api2.max.ru`), заголовок `Authorization: {MAX_BOT_TOKEN}`, `Content-Type: application/json`.
- Адрес — `chat_id` передаётся как query-параметр; тело — `{"text": "<plain text>"}`.
- Текст ≤ **4000 символов**, HTML-теги **удаляются**; превышение длины отклоняется до HTTP-запроса.
- **Троттлинг**: не чаще одного запроса в 0.5 с (лимит MAX — не более 2 сообщений/с в один диалог).

### 3.4. Ретраи

- Временные ошибки (`5xx`, сетевые, таймауты) — **retryable**, повторяются с **экспоненциальной задержкой** (1с → 5с → 25с).
- Критические ошибки (`4xx`) — **без повторов** (некорректная авторизация/адресат/сообщение).

### 3.5. Логирование и отслеживание доставки

Каждая попытка фиксируется в `NotificationLog`:

- привязка к `patientId` / `treatmentId`;
- `channelType`, `recipientAddress` (фактический адрес доставки);
- `priority`, `templateCode`;
- `status` (`sent` / `failed`), `errorMessage`;
- `externalId` — идентификатор сообщения во внешнем канале. Для MAX он остаётся `null`: API не возвращает id сообщения, поэтому успешный ответ (2xx) трактуется как `sent`.

## 4. Привязка `chat_id` пациента через защищённый диплинк

### 4.1. Зачем диплинк

`chat_id` — это ID диалога в MAX, и бот узнаёт его только из **входящих событий** (когда пациент сам написал боту). Чтобы связать этот `chat_id` с конкретным пациентом, врачу выдаётся **защищённый диплинк** с секретным токеном. Это и есть реализация «персонального кода» из письма куратора.

### 4.2. Поток привязки

1. Врач (JWT) запрашивает `GET /api/patients/{id}/max-deeplink` → получает ссылку `https://max.ru/<бот>?start=<token>`.
2. Токен — случайный (`bin2hex(random_bytes(16))`, 32 hex-символа), хранится в таблице `max_deeplinks` (`patient_id`, `token`, `created_at`) с уникальными индексами на `patient_id` и `token`.
3. Пациент открывает бота по диплинку — MAX присылает событие `bot_started` с `payload = <token>` (значение `start`) и `chat_id` диалога.
4. Обработчик резолвит токен в `patientId` через `MaxDeepLinkRepository::findByToken()`; **если токен не найден — событие молча игнорируется**.
5. Создаётся или обновляется `PatientChannelIdentity` (`channelType = "max"`, `value = chat_id`) для пациента из диплинка.

### 4.3. Персональный код = токен диплинка (не `chat_id`)

| Понятие | Назначение | Направление |
| --- | --- | --- |
| **Токен диплинка** (`max_deeplinks.token`) | секрет, по которому система **идентифицирует пациента** при обращении к боту | входящее |
| **`chat_id`** (`PatientChannelIdentity.value`, канал `max`) | адрес, **куда** система шлёт уведомления пациенту | исходящее |

Пациент видит только токен и никогда не узнаёт свой `patientId`, поэтому **подобрать чужой диплинк перебором нельзя**.

## 5. Входящий канал: Long Polling и Webhook

### 5.1. Long Polling (для разработки/отладки)

- Опрос `GET /updates` с фильтром типов `bot_started`.
- Команда `app:communication:collect-max-contacts` (разовый запуск или режим `--loop`).
- В `docker-compose.yml` поднят контейнер-слушатель `max-updates-listener` (аналог `messenger-worker`).
- Маркер последнего обработанного обновления хранится в файле `var/max_updates_marker`, чтобы не обрабатывать события повторно.

### 5.2. Webhook (для production)

- Эндпоинт `POST /api/max/webhook` — **публичный**, но проверяет заголовок `X-Max-Bot-Api-Secret` через `hash_equals` (неверный секрет → `403`).
- Активируется **только на деплое**: подписка регистрируется командой `app:communication:max-webhook-subscribe` (нужен публичный HTTPS-URL).
- MAX разрешает только один механизм — после активации Webhook Long Polling отключается.

## 6. Связь с ЭИБ и уведомлениями

- **Регистрация в истории болезни:** отправленный вызов и скорректированная рекомендация фиксируются в `notification_log` с привязкой к пациенту/лечению — это след в ЭИБ (пп. 2, 8 письма).
- **Данные пациента:** доза, внесённая пациентом через бота (4.3), будет отмечаться отдельным источником (п. 6).
- **Отслеживание доставки:** статус `sent`/`failed` и `externalId` позволяют отслеживать доставку рекомендации на телефон пациента и формировать отметку в истории болезни (п. 8).
- **Видимость для врача:** последнее отправленное сообщение/статус доступно в карточке пациента (связано с задачей `2.30`).

## 7. Безопасность

- **Диплинк** передаёт случайный токен, а не `patientId` — чужие диплинки не подбираются.
- **Webhook** проверяет `X-Max-Bot-Api-Secret` через `hash_equals` (защита от атаки по времени сравнения).
- **Секреты** (`MAX_API_URL`, `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `MAX_BOT_NICKNAME`) — только в корневом `.env` (в `.gitignore`); в git — только заглушки `.env.dist` и `api/.env.test`.
- **HTTPS к MAX** — по цепочке сертификатов Минцифры (`Russian Trusted Root CA` → `Russian Trusted Sub CA`), корневые добавлены в образ (`docker/php/certs/`).

## 8. Словарь терминов

| Термин | Определение |
| --- | --- |
| **Канал связи (channel)** | способ доставки уведомления: `sms`, `email`, `push`, `max`. |
| **Контакт канала (`PatientChannelIdentity`)** | адрес пациента в конкретном канале (телефон/email/push-токен/chat_id). |
| **`chat_id`** | идентификатор диалога/чата в MAX; адрес, куда отправляется сообщение. |
| **Диплинк MAX** | ссылка `https://max.ru/<бот>?start=<token>` для привязки пациента к боту. |
| **Токен диплинка (персональный код)** | случайный секрет, по которому система идентифицирует пациента при обращении к боту. |
| **`bot_started`** | событие MAX о первом обращении пользователя к боту (содержит `payload` = токен и `chat_id`). |
| **Long Polling / Webhook** | два механизма приёма входящих событий MAX. |
| **ЭИБ** | электронная история болезни; в неё регистрируются действия врача, анализы и данные пациента. |
| **`NotificationLog`** | журнал попыток доставки уведомлений (статус, адрес, канал, внешний id). |
